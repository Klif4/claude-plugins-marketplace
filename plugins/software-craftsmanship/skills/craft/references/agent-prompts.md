# Agent injection templates

Fill the placeholders and pass the result as the subagent prompt. Each launch is a
new call to the subagent-launching tool (`Agent`, named `Task` in some versions),
with the matching `subagent_type` — never a message to an agent that already ran.

| Role | `subagent_type` |
|---|---|
| Gherkin | `software-craftsmanship:bdd-writer` |
| Tests | `software-craftsmanship:test-writer` |
| Implementation | `software-craftsmanship:implementer` |

Drop the `software-craftsmanship:` prefix if the runtime does not namespace plugin
agents. The craft conventions are **not** restated in these templates: they live in
the agent definitions, and a second copy in the prompt would drift from the first.

## Why these templates stay short

Every agent starts with an empty context, so whatever the template lists is what
the agent will read. Listing the path of every file written so far makes the cost
of an iteration grow with the size of the code already written: three paths at the
first feature file, eighty at the tenth, twice over per file.

So the templates hand over **`.craft/api-map.d.ts`** — the signatures of
`src/domain`, generated by `yarn craft:map` — plus at most one file as a style
reference. The map says what exists; the agent opens the two or three real files it
actually needs. That is a bounded cost per iteration instead of a growing one.

The one thing that *is* injected in full is the feature file being driven: it is
the specification of the iteration, it is a hundred lines or so, and its scenarios
have to be read as a whole for the design to come out coherent. Never inject a
second feature file beside it.

Never re-add a "here is every existing file" list next to the map. The map replaces
that list — beside it, it is just more tokens.

## bdd-writer

```
Write the Gherkin scenarios for this business need.

BUSINESS NEED
<verbatim need, as the user stated it>

EXISTING SCENARIO TITLES — the vocabulary already in use, reuse it exactly
<output of: grep -rnE '^[[:space:]]*(Scenario|Scenario Outline):' features --include='*.feature'>

Open a .feature file only if you are adding to it. Do not read them all: the titles
above are what carries the vocabulary.

TARGET FILE
features/<domain>.feature

One file per business capability. The loop drives one file per iteration and
commits it as one commit, so a capability that would need thirty scenarios belongs
in two files, split along the business rules, not in one.

Everything in English. Real values, no placeholders. Business intent only: no UI,
no database, no HTTP. Cover the nominal case, the exact boundaries of every
threshold, and the business refusals.

Return, per file written, its path and the numbered list of its scenarios with
their exact titles, in file order.
```

## test-writer

```
Write the executable tests for this feature file — all of its scenarios. Tests
only — never src/.

FEATURE FILE
<path>

ITS CONTENT (verbatim)
<the whole file: Feature block, Background if any, Rules, every Scenario and
Scenario Outline with its Examples table>

SCENARIOS TO COVER
<the numbered list of its scenario titles, in file order>

Every scenario above needs its step definitions and the unit tests it makes
necessary. A scenario left undefined fails the gate.

WHAT ALREADY EXISTS
.craft/api-map.d.ts — every public signature of src/domain, generated from the
code. Read it first: reuse what is there rather than inventing a second name for
it. Open a source file only when you need a contract the signature does not state.
<omit these two lines entirely if the map does not exist yet — nothing exists yet>

STYLE REFERENCE — follow its shape, do not read further than these
Steps: <path of the most recently written file under features/steps/>
Unit:  <path of the most recently written file under tests/>

ORDER
1. Step definitions in features/steps/, asking the UseCaseFactory for the use cases
   the scenarios exercise, with in-memory adapters from
   features/steps/support/fakes/ and a clock fixed at each scenario's date.
   Write them for the whole file: the scenarios share a vocabulary, so they share
   their steps — one parameterised step beats five one-off sentences.
2. Then the Vitest unit tests in tests/ that those steps make necessary.

Build use cases through the UseCaseFactory, never with `new`. Every date comes from
@js-joda/core, written as a literal — never computed from the current date. Step
definitions assert with `import { expect } from 'vitest'` — nothing is global
under cucumber.

features/steps/ must not import anything from tests/. Each suite owns its fakes;
duplication between the two is intended.

It is expected that this does not compile — the types do not exist yet. Never use
any, as unknown as, @ts-ignore or @ts-expect-error to work around that.

Do not search wider than features/, tests/ and src/domain/. Never glob `**/*`.

Confirm the failure is real, with the feature-scoped gate and nothing heavier:
yarn craft:verify:fast --feature <path> <the tests/ files you wrote>

Return the exact paths written, the scenarios each one covers, and the API the
implementation will have to provide.
```

## implementer

```
Make this test suite green. Production code only — never touch a test.

FEATURE BEING DELIVERED
<feature title> — <path of the .feature file>

TEST FILES THAT SPECIFY IT
<paths from `git diff --cached --name-only -- tests features`>

Read those files: they are the specification and they are authoritative. They cover
every scenario of that feature file, and all of them must go green. You did not
receive their author's reasoning, and you do not need it.

WHAT ALREADY EXISTS
.craft/api-map.d.ts — every public signature of src/domain, generated from the
code. Read it before writing: it tells you what to reuse and what to extend.
Open the real file of any type you are about to depend on or modify — the map
states shapes, not behaviour. Do not read further than that.
<omit these lines entirely if the map does not exist yet>

CONSTRAINTS
- Write only under src/. Never modify, delete, skip or weaken a test.
- src/domain/** must reach 100% coverage. An uncovered branch is code nobody asked
  for: delete it. If it is legitimate behaviour with no test, report it — do not
  add a test.
The craft rules themselves are in your definition; they are not repeated here.

Do not search wider than src/ and the test files listed above. Never glob `**/*`.

VERIFY — this feature file only. Never run yarn craft:verify: the whole suite and
the coverage gate are the orchestrator's, run once at the end of the iteration, and
running them here costs minutes per attempt.
yarn craft:verify:fast --feature <path> <the tests/ files listed above>

Return the files written, the last lines of that command, and any test you believe
is wrong — without having modified it.
```

### Relaunching after a red gate

A red gate over a whole feature file points at a diff spanning its scenarios, so a
relaunch prompt adds the gate's own words to the template above:

```
THE GATE IS RED
<the tail the gate printed, verbatim>

FAILING SCENARIOS
<their exact titles>

FAILING TEST FILES
<their paths>
```

Nothing else. Not your reading of why it failed — the tail and the names are what
send the fresh agent to the right place, and an interpretation on top of them is
what makes it code to the interpretation.

## Never inject

Into the **implementer**, never inject:
- the test-writer's report, its designed-API summary or its rationale;
- an explanation of what the tests "mean" or what they are "trying to" specify;
- the Gherkin scenario bodies — the feature title and path are enough to name the
  commit, and the tests are what specifies the behaviour.

The implementer must read the tests. Handing it an interpretation of the tests lets
it code to that interpretation, and the gap between the interpretation and the
assertions is where bugs settle.

Into the **test-writer**, never inject:
- existing implementation source that already solves a scenario;
- a suggested API shape from this session.

The test-writer designs the API from the scenarios. Showing it an implementation
first turns outside-in design into after-the-fact test writing.

Into **any** of the three, never inject:
- the list of every file written so far — that is what `.craft/api-map.d.ts`
  replaced, and it is what made late iterations slow;
- a feature file other than the one being driven;
- the content of a source file the agent can open itself.
